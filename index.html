为什么收口 — 三个动因

  • 性能：13 个 subprocess fork → 1 个 (Claude Code 每 PreToolUse 都触发，13× 启动开销可感)
  • 可审计：5 group 的 decision 聚合到一份 ledger，diff 一目了然
  • 原子升级：换一个 detector 不影响其他，shadow mode 跑 5 天数据再 cutover

Shadow → Cutover 协议

  1. Ship dispatcher，settings.json 注册新 entry，保留旧 13 hooks 并行跑
  2. Dispatcher 落 shadow-events.jsonl，schema v2 (含 would_emit / would_block 字段)
  3. 5 天后跑 dispatcher-cutover-analyzer.py：per-group activation ≥ 30 + error_rate < 0.5% + BLOCK FN = 0 (compliance gate 零容忍) + inject FN ≤ 5%
  4. analyzer exit 0 = GO → 删 settings.json 旧 13 entries + archive 旧 hook 文件 + 切 enforce mode
2026-05-24 实战陷阱：v1 ledger 不记 would_emit_* 字段 → cutover metric "diff rate < 5%" 数学上无意义（always-pass shadow 对比 old-real-emit）。 Fix：schema 改 v2 + 直接对比 per-group decision 而非 final emit。KB 沉淀 shadow-mode-dispatcher-cutover-metric-trap.md。

Pattern 3 · Closed-loop Claim (DoD 漂移元缺陷)

3 layers + 4 维 checklist

2026-04-15 → 2026-04-29 反复发生："本地命令 exit 0" 当 "任务完成"。 DoD (Definition of Done) 应绑世界状态不绑自己 action exit code。 闭环宣告必须经独立 critic — 自查天花板 60-70%（KB 量化），剩余 30-40% 必须独立视角。

L1alignment-gate (UserPromptSubmit) — 多任务 prompt 必须有优先级声明advisory
L2closed_loop_tracker.py 6 步契约 — record_claim → record_change → attach_review → add_finding → set_disposition → check_verifiedschema
L3Stop hook Rule 5(j) verify-session — closure claim 必经外审 critic + finding disposition + time+scope 绑定 → exit 1 blockedFLOOR

4 维 checklist (任一缺失 = not closed-loop)：

  • Schema 对照 — 所有 JSON/file 对照 SCHEMA.md/spec，enum 值合法
  • 全 caller 扫描 — grep import + call sites 全更新/兼容
  • End-to-end 真实路径 — 真 subprocess/API/hook 跑过，不接受 mock-only
  • 历史回查 — audit log / state file / commit history 有 trace 证明真发生

措辞分级 (GPT 外审 P0 #9 修正)：implemented (代码写完) ≠ verified (外审过) ≠ closed-loop (verified + Tian ack)。部署 gate / hook 后默认只能说 implemented。

06架构原则 · 8 周沉淀

这些不是先验设计原则，是从一次次"为什么这条 rule 又被忽略了" 反推出来的。每条都对应至少一个 KB wiki 实证。

01

Deterministic > LLM

能用代码做的判断不让 LLM 做。Hook 性能 + 确定性 100% + 可 unit test。LLM 留给语义/分类/生成。rules/deterministic-first.md

02

Hard-block > Advisory (94% 天花板)

advisory hook 在高置信错误上有 ~94% 失败率天花板。recurring 问题必须 direct hard-block + override + weekly audit，不走 28 天观察期。Tian 2026-05-08 reframe。

03

Closed-loop with External Critic

自查天花板 60-70%。任何 closure claim 必经 challenger / GPT 外审 + finding disposition + time-scope 绑定。closed_loop_tracker.py 6 步契约。

04

Mechanism-first, No Sycophancy

3 个元缺陷 (Meta Failure Modes)

M1 · DoD 漂移元缺陷 (2026-04-15 诞生)
Self-model 把 "完成" 绑在 own action exit code 而非 world state。 修完本轮 DoD 漂移的同一会话忘了 "GPT 联动 harness 同步" 就是换变体实证。 修复机制：每次声明完成前必问 "我画的边界是否比现实世界的边界更小"。
M2 · 失败模式换变体重犯
修完一个具体 case 后，同一根因换变体在下一个会话复发。fix 不带 mechanism 理解 → 同模式必然重犯。 修复机制：fix 时强制做 ≥3 段机制分析 + KB sediment (不是 action item)，让下次 distribution shift。
M3 · Distribution Prior > Read Instruction (94% ceiling)
训练 distribution prior 在 query 生成 / 选项默认 / autocomplete 时压过 prompt 里写的 rule。 即使 SessionStart 顶置 + UserPromptSubmit reminder + grounding 例 17 同时部署，仍可能违反。 修复机制：advisory 永远只是降低触发率 — 真正的 floor 必须是 deterministic hard-block (L3 gate)。
